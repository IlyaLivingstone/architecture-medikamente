# Аналитический слой с учётом Privacy by Design

Цель аналитики — извлекать из данных знания для бизнеса (отчёты, прогнозы, ML-модели), а не
раскрывать личности пациентов. Поэтому аналитический слой проектируется так, чтобы в него
попадали только нужные и при этом обезличенные данные, а путь каждого набора был прозрачен.

## Принцип работы

В озеро данных попадают не сырые операционные данные, а данные, прошедшие через подготовку:
сначала классификация тегами, потом обезличивание, потом загрузка. Аналитик физически не
имеет доступа к исходным ФИО и телефонам — только к псевдонимам, возрастным группам и
агрегатам.

## Слои

### 1. Слой загрузки и подготовки

Здесь три шага, и все обязательные:

- **Минимизация.** Из операционных систем забирается только то, что реально нужно для
  аналитики. Полные медкарты целиком не копируются — только поля, перечисленные в политике.
- **Классификация и тегирование.** Входные данные размечаются тегами `PII`, `PHI`, `FIN`.
  Данные, у которых нет тега или которые запрещены для аналитики политикой, на этом шаге
  отбрасываются.
- **Обезличивание.** Прямые идентификаторы удаляются (ФИО, телефон, email), квази-
  идентификаторы обобщаются: дата рождения становится возрастной группой, адрес — районом.
  Пациент получает сквозной псевдоним, одинаковый во всех витринах, чтобы аналитика по
  одному человеку была связанной, но без раскрытия личности.

### 2. Озеро данных с зонами

Озеро делится на зоны с разным уровнем доступа:

- **Raw** — обезличенные данные в исходном виде, доступ только у инженеров данных.
- **Processed** — очищенные, валидированные, с метками. Источник для всех дальнейших
  витрин.
- **Curated** — готовые наборы для BI и ML: агрегаты, признаки, витрины.

Такое деление (из урока про слои данных) позволяет, с одной стороны, не терять исходные
обезличенные данные, с другой — не пускать аналитиков в сырьё, где риск выше.

### 3. Золотой источник

Отдельно от озера хранится золотой источник — эталонные операционные данные (актуальный
справочник пациентов, услуг, платежей). Важно не смешивать его с аналитическим озером: у
них разный режим доступа и разные требования к актуальности. Аналитика читает из озера, а
не из золотого источника, чтобы нагрузка и риск не пересекались.

### 4. BI, ML и AI поверх озера

BI-инструменты строят отчёты по витринам Curated-зоны. ML-модели обучаются на обезличенных
наборах, а при нехватке данных — на синтетических, сгенерированных с сохранением
статистики, но без реальных людей. Это закрывает сценарий «обучить модель, не трогая
реальные данные пациентов».

## Что обеспечивает конфиденциальность на каждом шаге

- **Тег `ANONYMIZED`** проставляется каждому набору, прошедшему обезличивание, вместе с
  метаданными о методе и дате. Набор без тега не выдаётся наружу.
- **Data Lineage** фиксирует путь данных от операционной системы через все зоны до отчёта.
  Если в отчёте ошибка — видно, на каком этапе она возникла. Если поступил запрос на
  удаление — видно, в каких витринах лежат данные человека.
- **Доступ по ролям** разведён: инженер данных видит Raw, аналитик — Processed/Curated,
  внешние системы — только согласованные витрины.
- **Маскирование в отчётах** как страховка: даже если в отчёт попало что-то лишнее, оно
  показывается усечённым.

## Технологии

Загрузка и обезличивание — Python или Spark (объёмы пока небольшие, Spark нужен на вырост).
Хранение — объектное хранилище (S3-совместимое) для Raw/Processed и колоночная БД для
Curated-витрин. Для тегов и прослеживаемости — Apache Atlas, он закрывает и тегирование, и
Data Lineage в одном месте.
