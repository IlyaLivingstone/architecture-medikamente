# Метрики эффективности и масштабирование

## Метрики: что измеряем

### Качество классификации

| Метрика | Что показывает | Целевое значение |
|---|---|---|
| Полнота разметки | доля наборов и полей, у которых есть тег | 100% для новых наборов, рост для исторических |
| Точность (precision) | доля верных срабатываний среди тех, где классификатор присвоил класс | не ниже 0,95 по критичным классам |
| Полнота (recall) | доля найденных конфиденциальных полей из всех, что там реально есть | не ниже 0,98 по медданным |
| Ошибка между классами | случаи, когда `PII` и `PHI` перепутаны | стремимся к нулю: цена ошибки выше, чем при пропуске тега |
| Ложные срабатывания | доля полей, размеченных как конфиденциальные, хотя они такими не являются | контролируем, но не в ущерб полноте |
| Пропуски | доля конфиденциальных полей, оставшихся без тега | измеряется на аудиторской выборке |

Precision и recall измеряются не «на глаз», а на контрольной выборке, которую раз в месяц
размечает вручную владелец данных. Без этого метрики превращаются в самооценку.

**Важная асимметрия.** Для нашего кейса пропуск опаснее ложного срабатывания: не найти
диагноз в выгрузке — это утечка медданных, а лишний раз отправить безобидное поле на разбор —
это только потраченное время ревьюера. Поэтому пороги настраиваются в пользу полноты: лучше
отправить набор в карантин, чем пропустить конфиденциальное поле.

### Работа конвейера

| Метрика | Что показывает |
|---|---|
| Доля набора в ручном разборе | сколько данных не доходит до аналитики без человека |
| Время ручного разбора (SLA) | сколько ждёт набор в очереди: если растёт, аналитика стагнирует |
| Доля дрейфов, обработанных автоматически | насколько реестр схем справляется без вмешательства |
| Время от появления данных до доступности в curated | общая задержка конвейера |
| Стоимость классификации на гигабайт | сколько стоит каждый прогнанный объём |

### Результат для бизнеса

| Метрика | Что показывает |
|---|---|
| Число инцидентов из-за неверной разметки | цель — ноль; любой инцидент разбирается письменно |
| Доля выгрузок, отклонённых шлюзом политик | показывает, что контроль работает, а не только существует |
| Число запросов на удаление, выполненных из всех зон | проверка, что данные действительно удаляются везде |

## Как метрики приводят к оптимизации

Метрики нужны не для отчёта, а для конкретных действий. Связка «симптом — что делаем»:

- **Полнота падает.** Появился тип данных, которого нет ни в правилах, ни в обучении. Добавляем
  правило или дообучаем модель на новых примерах из очереди разбора.
- **Точность падает.** Правила стали слишком широкими: например, поле с суммами ловится как
  номер карты. Уточняем шаблон, чтобы не гонять на разбор лишнее.
- **Растёт доля ручного разбора.** Узкое место в правилах: если один и тот же тип поля
  постоянно уходит на ревью, значит, для него пора завести правило или признак в модели.
- **Время разбора выше SLA.** Очередь копится, и данные не доходят до аналитики. Расширяем
  круг ревьюеров или снижаем порог автопринятия там, где ошибка дешевле задержки.
- **Много дрейфов схем.** Источник живёт своей жизнью. Идём к владельцу источника и
  фиксируем контракт на структуру, вместо того чтобы бесконечно чинить последствия.
- **Растёт стоимость на гигабайт.** Переходим на инкрементальную классификацию и кеш
  результатов по профилю, а ретроспективную переклассификацию уводим в непиковые часы.

Раз в месяц по этим метрикам пересматриваются пороги и правила. Это не разовая настройка:
источники меняются, и классификатор вместе с ними.

## Масштабирование

### По объёму данных

**Сэмплирование вместо полного прохода.** Движок не читает весь набор: сначала метаданные и
профиль, затем выборка значений. Полный проход по колонке делается только там, где выборка
дала неоднозначный результат. Это главный рычаг экономии: рост объёма в пять раз не означает
пятикратного роста времени классификации.

**Инкрементальная обработка.** Классифицируются только новые и изменившиеся поля. Результат
кешируется по паре «версия схемы + профиль»: если структура и распределение не изменились,
берётся готовый вердикт. Полная переклассификация запускается по расписанию или по запросу
после изменения правил.

**Горизонтальные воркеры.** Обработка наборов распараллелена: воркеры не хранят состояние,
результаты пишутся в каталог метаданных. Число воркеров растёт вместе с числом наборов,
а не с их размером. Один тяжёлый набор разбивается на партиции по строкам.

**Партиционирование зон.** Landing, quarantine и curated разбиты по домену и дате, что даёт
параллельную запись и возможность удалять данные по сроку целыми партициями, а не построчно.

### По числу пользователей и источников

- **Доступ по тегам** не требует пересматривать права при появлении нового набора: права
  выданы на класс данных, а не на таблицу.
- **Витрины вместо сырых зон.** Аналитики работают с mart-зоной; рост числа пользователей
  увеличивает нагрузку на витрины, а не на restricted-зону.
- **Новые источники подключаются через тот же конвейер.** Добавление источника — это новый
  коннектор и запись в реестре схем, а не новый процесс.
- **Пропускная способность очередей.** Если очередь ручного разбора не успевает, это не
  ломает конвейер: наборы ждут в quarantine, аналитика получает меньше данных, но сырые
  конфиденциальные данные в хранилище не попадают. Отказ происходит «в безопасную сторону».

### Что делаем при резком росте

1. Проверяем, не выросла ли доля ручного разбора: если да, расширяем правила — это дешевле,
   чем добавлять воркеры.
2. Увеличиваем число воркеров классификации и партиций обработки.
3. Включаем приоритизацию: сначала свежие домены, исторические наборы переклассифицируются
   ночью.
4. Если упираемся в стоимость, снижаем частоту ретроспективной переклассификации и оставляем
   её только для наборов, где менялись правила.

## Границы масштабирования

Масштабируется всё, кроме одного: **ручной разбор**. Ревьюеров нельзя «добавить воркерами»,
поэтому цель системы — постоянно снижать долю данных, которая доходит до человека. Если эта
доля не падает, значит, правила и модель отстают от изменения источников, и это отдельная
задача на оптимизацию, а не вопрос мощностей.
