# Базовые инструменты защиты данных

Инструменты сгруппированы по состоянию данных, потому что они не заменяют друг друга:
шифрование диска не защищает трафик, а TLS не защищает данные, уже загруженные в память.
Ниже — что именно предлагаю внедрить в «Медикаменте» и от какой угрозы каждое средство
закрывает.

## Данные в покое

Здесь угрозы простые: украли диск, скопировали файл на флешку, унесли резервную копию.
Против них работает шифрование при сохранении.

- **Полное шифрование диска (FDE).** BitLocker на рабочих станциях, LUKS на серверах.
  Закрывает кражу носителя целиком: без ключа диск не читается. Дешевле всего в внедрении,
  потому что не требует правок в приложениях.
- **Самошифрующиеся диски (SED).** Шифрование на уровне железа: ключ живёт в контроллере
  диска, процессор не тратит ресурсы. Берём на новые серверы и ноутбуки сотрудников.
- **Шифрование базы данных (TDE).** AES-256 на уровне PostgreSQL: файлы БД на диске
  зашифрованы, приложение работает как обычно. Это основной инструмент для операционной БД
  из целевой архитектуры.
- **Шифрование отдельных колонок.** Для диагнозов, паспортных данных, ИНН и СНИЛС — тех
  полей, где недостаточно защиты всей БД. Даже администратор базы не должен видеть их в
  открытом виде в консоли.
- **Шифрование объектного хранилища (SSE-KMS).** Сканы паспортов, медкарты, результаты
  анализов лежат в S3; включаем серверное шифрование с ключами из KMS.
- **Шифрование резервных копий.** Бэкап — это копия тех же данных, и по статистике именно
  он чаще всего оказывается незащищённым. Шифруем и бэкапы, и изолированное хранилище.

## Данные в передаче

Угрозы здесь — перехват, подмена и прослушивание, особенно когда данные идут через
публичную сеть или через внешнюю систему вроде лаборатории.

- **TLS 1.3 для всех каналов.** Внешние интеграции, трафик от браузера, обмен между
  сервисами. Старые версии (TLS 1.0, 1.1, SSL) отключаем совсем: они дают ложное чувство
  защиты и при этом уязвимы.
- **mTLS для межсервисных вызовов и лаборатории.** Обычный TLS подтверждает, что клиент
  говорит с правильным сервером, но не подтверждает сам клиент. Для API-контракта с
  лабораторией и между внутренними сервисами нужен взаимный сертификат.
- **Замена устаревших каналов.** Связка «касса - 1С» на TCP/IP через OLE и приём результатов
  анализов по почте несовместимы с требованиями к персональным данным. Обе заменяются на
  API + TLS; почта для медданных закрывается как канал.
- **VPN для административного доступа.** Админы подключаются во внутреннюю сеть только через
  WireGuard с отдельной учётной записью. Дополнительно — jump host с журналированием
  сессий, чтобы действия администраторов не были анонимными.
- **SSH вместо telnet и FTP.** Там, где осталось управление сервером, только SSH с ключами
  и без парольного входа.
- **Сертификаты.** Свой внутренний CA для внутренних сервисов, публичный — для внешних.
  Отслеживаем сроки, ротация автоматическая; просроченный сертификат не должен превращаться
  в отключение TLS «чтобы работало».

## Данные в использовании

Самое сложное состояние: данные должны быть доступны приложению, значит, где-то они лежат
в памяти открытыми. Задача — сузить это окно и уменьшить объём.

- **Шифрование на уровне приложения.** Платёжный модуль расшифровывает реквизиты только на
  время операции и сразу затирает буфер. Это защищает от скрапинга памяти.
- **Токенизация.** Реальные значения не хранятся в операционных таблицах, которые читают
  большинство сервисов: вместо паспорта и карты — токен. Расшифровка возможна только в
  одном сервисе, у которого есть ключ.
- **Минимизация данных в памяти.** Приложение обрабатывает текущий набор записей, а не
  выгружает всю таблицу; для отчётов использует витрины, а не операционную базу.
- **Проверка доступа на каждом обращении.** Права проверяются не один раз при входе, а на
  каждом запросе к данным с учётом роли и атрибутов (кто врач, чей пациент). Это закрывает
  инсайдерский сценарий: сотрудник с валидной учёткой всё равно не получит чужую карту.
- **Доверенные среды исполнения (TEE).** Intel SGX оставляю как опцию на будущее для
  отдельных операций — технология дорогая и сложная, для текущих объёмов клиники
  достаточно прикладного шифрования и токенизации.
- **Безопасное кодирование.** Параметризованные запросы, проверка входных данных,
  ограничение размера ответов. Это не про шифрование, но без этого любые ключи бесполезны.

## Управление ключами

Шифрование без управления ключами не работает: ключ, лежащий рядом с данными, защищает не
лучше пароля на стикере.

- **KMS / HashiCorp Vault** — центральное хранение ключей и секретов, приложения получают
  ключ по API на короткое время и не хранят его у себя.
- **HSM** для мастер-ключей, из которых выводятся остальные. Аппаратный модуль не даёт
  выгрузить ключ наружу.
- **Разделение по средам.** Ключи продакшена и тестового контура разные; тестовые данные
  зашифрованы своими ключами, и утечка тестового ключа не открывает прод.
- **Ротация и срок жизни.** Регулярная смена ключей и отдельных ключей для разных типов
  данных: компрометация одного не раскрывает всю базу.
- **Аудит доступа к ключам.** Кто и когда запрашивал ключ — событие уровня безопасности,
  оно уходит в SIEM наравне с доступом к медданным.

## Как выбирались методы

Четыре фактора из теории, приложенные к нашему случаю:

| Фактор | Решение для «Медикаменте» |
|---|---|
| Производительность | AES-256 для хранения и каналов (быстрый, аппаратно ускоряется), RSA только для рукопожатия TLS. Гомоморфное шифрование не берём: для наших объёмов это неоправданно дорого |
| Совместимость | FDE и TDE не требуют правок приложений, поэтому внедряются на текущем стеке. Токенизация требует изменений в платёжном модуле — это уже в целевом контуре |
| Требования регуляторов | 152-ФЗ и 323-ФЗ для медданных, PCI DSS для платёжных реквизитов: AES-256 и регулярная ротация ключей |
| Управление ключами | Единый Vault вместо ключей в конфигах; мастер-ключ в HSM |
