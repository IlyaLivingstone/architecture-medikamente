# Механизм тегирования данных

Тегирование — это способ пометить данные, чтобы дальше на эти метки завязать автоматику:
кому доступ, что шифровать, что маскировать, что удалять по сроку. Для «Медикаменте» это
базовый механизм, без которого не получится ни разграничить доступ, ни автоматизировать
защиту в новой системе.

## Какие теги вводим

Набор тегов сознательно небольшой, чтобы им реально пользовались, а не городили справочник:

| Тег | Что означает | Пример |
|---|---|---|
| `PII` | Персональные данные (152-ФЗ) | ФИО, телефон, адрес, дата рождения |
| `PHI` | Медицинские данные (спецкатегория, врачебная тайна) | Диагноз, назначения, результаты анализов |
| `FIN` | Финансовые данные | Сумма платежа, зарплата, задолженность |
| `HR` | Кадровые данные сотрудников | Паспорт, ИНН, СНИЛС |
| `CONF` | Коммерческая информация | Стоимость ТМЦ, поставщики, договоры |
| `INTERNAL` | Служебное, без ограничений внутри компании | Графики, журналы без ПДн |
| `PUBLIC` | Публичное | Прайс, информация о компании |

Для части данных теги сочетаются: медкарта — это `PHI` + `PII` одновременно, потому что в
ней есть и диагнозы, и ФИО с контактами.

## Как устроен процесс

Разметка — не разовое действие, а процесс, встроенный в работу с данными. По шагам:

1. **Инвентаризация.** Понять, где какие данные лежат. Сейчас это можно сделать вручную по
   описанным выше процессам: Excel-файлы, папки пациентов, 1С, почта.
2. **Классификация.** Каждому набору данных — тег из таблицы. Здесь же определяем, что
   относится к спецкатегории по 152-ФЗ.
3. **Разметка.** Проставляем теги. На стадии «как есть» — вручную в реестре, в целевой
   системе — автоматически при создании данных и при загрузке из внешних систем.
4. **Доступ по тегам.** Связываем теги с ролями (RBAC) и атрибутами (ABAC). Например: роль
   «кассир» не имеет доступа к `PHI`, а врач — имеет, но только к своим пациентам (атрибут
   «лечащий врач»).
5. **Автоматика на тегах.** Тег запускает действия: `PHI` -> шифрование at rest, `PII` ->
   маскирование при показе, `FIN` -> аудит каждой операции.
6. **Аудит и обновление.** Проверяем, что всё размечено, теги не протухли, у данных с
   истёкшим сроком хранения тег меняется на «к удалению».

## Чем автоматизировать

На старте, пока системы нет, достаточно вести реестр в таблице — это уже даст общую картину.
Когда появится целевая система, разметку стоит автоматизировать, иначе при росте объёмов
данных вручную её не удержать.

Из платформ, разобранных в теории, под задачи «Медикаменте» логично смотреть так:

- **BigID** — если нужна автоматическая классификация большого объёма данных с машинным
  обучением. Дорого и тяжело во внедрении, для старта избыточно.
- **OneTrust / DataGrail** — если на первом месте управление согласиями и обработка запросов
  на удаление. Полезно, когда появится портал пациента и мобильное приложение.
- **Collibra** — если нужен единый каталог метаданных и визуализация потоков (Data Lineage).
  Хорошо ложится на цель «озеро данных для BI/AI».
- **Apache Atlas** — опенсорс, если компания пойдёт в Hadoop-стек. Бесплатно по лицензии,
  но требует людей, которые будут это сопровождать.

Для компании такого размера я бы начал не с дорогой платформы, а с простого реестра тегов +
правил в самой системе. Платформу класса BigID/Collibra подключать позже, когда данные
переедут в единое хранилище и их станет действительно много.

## Связь тегов с защитой

Теги — это не самоцель. Они нужны, чтобы защита применялась автоматически и одинаково во
всех процессах:

- `PII`, `PHI`, `FIN`, `HR` -> шифрование при хранении;
- `PII`, `PHI` -> маскирование при отображении пользователям без полного доступа;
- `PHI` -> ABAC (лечащий врач) + обязательный аудит чтения;
- `FIN`, `HR` -> RBAC по отделам + аудит изменений;
- все теги -> сроки хранения, по истечении которых данные удаляются или архивируются.

Так разметка превращается из «наклеек» в работающий механизм контроля, на который потом
можно опереться и при аудите соответствия 152-ФЗ, и при построении аналитики.
