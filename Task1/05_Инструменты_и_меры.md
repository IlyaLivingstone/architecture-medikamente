# Инструменты и меры по процессам

Свёл воедино, что именно предлагаю внедрить и на каком участке потока. Это тот же разрез,
что на TO-BE диаграммах, но в виде списка — по каждому бизнес-процессу.

## Общие меры (для всех процессов)

Эти вещи нужны независимо от конкретного процесса:

- **Шифрование в покое.** Полнодисковое шифрование сервера + шифрование файлов с ПДн (AES-256).
  Закрывает риск кражи сервера или копирования файлов.
- **Шифрование при передаче.** TLS 1.3 для всех каналов, где ходят ПДн: внутри сети и наружу.
- **Разграничение доступа.** RBAC по ролям, для медицинских данных — ABAC (доступ только
  лечащего врача к своим пациентам). Реализация — через AD сейчас, через IAM в целевой
  системе (например, Keycloak).
- **Аудит.** Журналирование доступа к медкартам и изменения финансовых данных. Без этого
  невозможно ни расследование, ни доказательство соответствия 152-ФЗ.
- **Резервное копирование с шифрованием.** Бэкапы не должны быть читаемыми.
- **Тегирование данных.** Теги `PII`/`PHI`/`FIN` и т. д. как основа для автоматики (см.
  `04_Механизм_тегирования.md`).

## По процессам

### Регистрация пациента

- Собирать только то, что нужно: убрать обязательные поля расширенной анкеты, оставить их
  опциональными для тех, кому это реально требуется.
- Ввод ПДн — в систему с контролем доступа, а не в общий Excel.
- Сканы паспорта — в защищённое хранилище с шифрованием и строгим доступом, а не в открытую
  папку на общем диске.

### Запись на приём

- Журнал записей — в систему с RBAC: ресепшен видит всё, специалист — только своих.
- Телефон пациента в журнале маскировать для тех, кому полный номер не нужен.
- Напоминания — через автоматические уведомления (в перспективе — мобильное приложение),
  а не через ручной обзвон с личных телефонов.

### Приём у врача

- Медкарта — в защищённом хранилище, доступ по ABAC (лечащий врач).
- Каждое чтение медкарты логировать.
- Диагнозы и назначения шифровать at rest.

### Лаборатория анализов

- С лабораторией — защищённый канал (TLS), а не пересылка файлов и бумаг вручную.
- Результаты в реестре хранить с маскированием ПДн: для аналитики ФИО не нужны.
- Подшивка результатов — в папку пациента с шифрованием.

### Оплата услуг

- Заменить OLE/TCP/IP между ККМ и 1С на защищённый API-канал.
- Реквизиты платёжных данных токенизировать.
- Убрать двойной учёт в Excel — один источник правды в 1С (позже — в новой системе).

### Бухгалтерский учёт

- Зарплаты и кадровые данные — отдельный контур доступа, только бухгалтерия.
- Отчётность в налоговую — по защищённому каналу.
- Кадровые сканы (паспорта, трудовые) — в защищённое хранилище с шифрованием.

### Складской учёт ТМЦ

- Разграничить доступ: склад работает с остатками, бухгалтерия — со стоимостью.
- Стоимость и поставщиков пометить тегом `CONF` и ограничить доступ.

## Выбор инструментов

| Задача | Инструмент | Почему |
|---|---|---|
| Разграничение доступа (IAM) | Keycloak / Azure AD | RBAC + ABAC, интеграция с тегами |
| Управление потоками данных | Apache NiFi | Автоматизация обмена, шифрование, provenance |
| Тегирование и классификация | Реестр тегов -> BigID/Collibra | Сначала просто, потом автоматизация |
| DLP (контроль утечек) | Symantec/McAfee DLP | Сканирование почты и файлов на ПДн |
| Аудит и мониторинг | Централизованный лог (например, ELK) | Сбор и алертинг по доступам |
| Хранение и аналитика | Защищённое озеро данных | База для BI/AI без прямых ПДн |

## Что даёт этот набор

Если меры внедрить по процессам, компания закрывает главные риски из аудита: конфиденциальные
данные перестают лежать в открытом виде, доступ ограничивается по ролям, появляется аудит, а
платёжный и лабораторный контуры переходят на защищённые каналы. При этом меры не требуют
сразу строить всю целевую архитектуру — часть из них (шифрование, разграничение файлов,
защита бэкапов) можно сделать на текущем ландшафте.
